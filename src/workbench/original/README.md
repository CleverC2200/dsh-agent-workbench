# Original GEA sales-plan workbench

Copied from AionUi `packages/desktop/src/renderer/pages/assistantSurface/workbenches/regionalApproval` at commit `55d12cd60248c6084afd76bba816638a79af36de` (Apache-2.0; retained in `LICENSE`). The source workbench is React and CSS Modules rendered inside `BusinessSurfaceShell`; there is no independent sales-plan HTML file in that checkout. The current build compiles this page through `src/workbench-entry.tsx` into `lib/native.js` and `lib/native.css`; Workbench presents it as a Native business document.

The original JSX, styles, query generation, exact-decimal projection, version comparison, dialogs and workflow models are retained. Changes redirect source imports to local files, make NodeNext file extensions and a numeric reducer type explicit, and replace the AionUi IPC and chat imports with `bridge.ts` and `session-context.tsx`. No AionUi process or conversation implementation is imported. `contracts.ts`, `salesPlanWorkflow.ts`, `http-error.ts`, `storage.ts`, and the surface translations are copied or extracted from their source owners. Storage prefixes are isolated to `gea-dsh`, so old AionUi browser state is not adopted.

Before mounting, call `bindWorkbenchHost(host)`. Supply all methods declared by `WorkbenchHost`; absence of a binding throws instead of rendering fabricated records. Pass `stateScope`, `t`, `onContextChange`, the authenticated `approvalStages` (账号角色映射出的可审批节点), and `liveActionsEnabled` to `RegionalApprovalWorkbench`. Wrap the component with `WorkbenchSessionProvider` using the actual DSH session ID. Publish the complete `onContextChange` value to the parent host; it includes selected rows, visible rows, scope, revision input, authority and evidence status.

The Native build bundles this page with React, ReactDOM, `@arco-design/web-react`, `@icon-park/react`, i18next, and `xlsx-republish`. Load Arco CSS, then `theme.css`, and compile `.module.css` with CSS Modules (`local-css` in esbuild). The two locale JSON files use an i18next `common` namespace. The copied workbench renders some legacy fixture code only when its query client is explicitly `null`; a live plugin must supply the host adapter, never `null`.

The host maps the original API methods to GEA: `GET periods`, `GET plans`, `GET plans/:planId`, `GET plans/:planId/versions`, `GET plans/:planId/logs`, `GET plans/versions/:versionId/skus`, and `GET plans/:planId/compare`. IDs and decimals remain strings. `action` uses the GEA version-action transport. `submit` is the method declared by `WorkbenchHost`; its service transport must satisfy the submission contract below and has a separate caller-authorization requirement. 审批身份只认账号角色：Host 经网关会话解析当前用户角色（region/province/area/category），映射成可审批节点交给界面；通知只做提醒，不授予身份，服务端返回的对象能力也只补充动作、不授予身份。角色决定能进哪些节点，数据权限决定明细；审批或退回仅限授权组织内的有效版本、相应账号角色及可处理状态。可见性本身不授予写权限，状态0/5/10及历史版本保持只读，最终仍由 GEA 写入接口按组织、角色、版本、状态和快照校验。Stage filters browse server-visible data independently of action permissions. 角色读取失败时该账号没有审批节点，界面只读。Stateless SKU advice uses `modelInference.invoke`; it is independent of the right-side DSH conversation.

Returned rows expose a resubmission dialog that reads the current version and SKU data, edits quantities, and validates the configured next status and original `orderType`. Customer returns require an OPEN period; approval-role returns do not inherit that client-side window restriction. The Host retains the authenticated user ID for attribution. The GEA returned-plan resubmission adapter is wired through its `salesPlanSubmit` method. Confirmation requires the current environment service identity, caller authorization and the expected plan state. Source wiring does not prove those credentials, the deployed service or live acceptance. This method handles returned-plan resubmission; first submission remains a separate uncompleted requirement. Local editing does not write business data. This is not a separate first-submission page.

The submission endpoint is `POST /api/v1/internal/sales-plans` under the shared first-submission and resubmission service contract. The current returned-plan adapter implements resubmission only; it does not provide a first-submission page. It requires service-identity Authorization, Idempotency-Key and X-Request-Id. A connected adapter must validate the caller, tenant and source version before invoking the service. The form retains one immutable attempt after dispatch and only retries an uncertain outcome with the same key. A receipt must identify the expected successor; readback must show that successor effective, its predecessor retired, and a matching RESUBMIT log before the queue is refreshed. Confirmation-field inheritance and live service authorization still require acceptance.

The business page loads workflow rows through `/api/gea-proof/workflow/config` before loading periods. The Host requires its current GEA login, keeps delegation tokens server-side, validates complete SQL paging and configured chains, and cancels reads on identity changes. Document loads reject aborted or superseded results; queue, progress and analysis queries require successful period loading. Configuration failure clears the workflow projection. Local workflow rows serve fixtures only in this document. XN and other shortened chains resume through their next configured node, including non-contiguous configuration levels; approval is independent of the submission window. These projections do not grant write authority.

Sales-plan action errors preserve the upstream HTTP status and sanitized diagnostic fields. A 409 response is a confirmed conflict, not an unknown transport outcome; the dialog shows the backend explanation, including unresolved workflow assignees. Transport uncertainty retains same-intent retry behavior.

SAVE requests carry a plan ID for Host-side preflight. The Host re-reads that plan under the current login, requires an explicit server SAVE capability, and checks the effective version, status and snapshot hash before writing. Status 5 is rejected before any save request. A changed snapshot after an unknown result prevents another write and requires reconciliation. The UI uses object capabilities independently of legacy menu roles; save readback also rejects changed sequences or plan types and unknown or duplicate adjustment codes.

The [V1.3 role-approval contract](../../../../dsh-gea-plugin/specs/sales-plan-role-approval-v1.3.md) supersedes the old status-10 SAVE requirement: status 10 is read-only. The current GEA checkout still has a compatibility SAVE branch for requests without `approvalRole` or `adjustmentMode`; it rejects status 5 explicitly and otherwise checks the server SAVE capability, effective version and snapshot. Removing this branch is an outstanding source migration, not a long-term target. Its presence does not prove V1.3 enforcement or deployed SAVE acceptance.

The historical backend `pro` observation at `cf388b27` exposed only APPROVE/REJECT with expectedStatus 1–9 and accepts active approval states 1–4 in the action service. It does not expose SAVE or an action snapshot field. That observation did not prove a deployed status-10 same-version SAVE contract. SAVE within the V1.3 permitted scope still requires separate deployment evidence and a real service receipt. The historical status-10 target and isolated Host/Chrome SAVE fixtures do not override V1.3 terminal-state read-only rules. Those fixtures verify the adapter and readback behavior only; they do not demonstrate a deployed SAVE contract or real persistence. DMS remains mock-only.

Sales-plan organization expansion and row selection use the same expanded state. Loaded SKU quantity, amount and description are published as their displayed values in the read-only page snapshot. Amount and description remain read-only and stay outside quantity batch updates. Snapshot publication and recovery do not save or approve plans.
