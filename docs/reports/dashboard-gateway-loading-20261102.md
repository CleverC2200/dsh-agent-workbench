# 客户库存与订单工作台：网关及查询加载优化（第二轮，2026-11-02）

本轮在上一轮改动上继续实施，使用当前货龄来源和计算版本 7。基线与候选均为本票隔离源码构建，读取用户授权的真实 GEA 数据；没有使用旧的已发布客户端，也没有发布、改正式运行目录、执行数据库 DDL 或扩大授权。

## 查到的瓶颈与落地改动

客户库存的旧分页每页最多 200 行；库存、计划、地址各 2728 行及负责人约 2249 行，使同一份汇总 SQL 反复执行。四份来源改为每 64 行一个传输组；每组保留来源总行数、组内行数和全局位置。通常一页即可承载完整客户范围，解包后再交给原映射、指标和分页逻辑。

订单工作台库存汇总超过 200 个维度组时，原路径额外执行计数和分页；新 `workbench.stock.summary.packets` 从原汇总 SQL 派生，同样按 64 行传输，保持基地、品类、品项、负责人和归属标志等完整分组。原始明细、SKU 页面、其他指标查询及六个周期均保留。

客户库存同时选择 Host 已支持的 `resultShape: rows`，避免通过页面桥重复发送相同的 `rows` 和 `records`。计数、返回列及拒列元数据保留；该选项单独进入读取合并键，其他调用默认协议不变。

网关兼容性通过真实只读调用逐项确认：JSON 构造表达式不能进行安全字段分析；本轮使用可分析的 CASE、CAST、CONCAT、LENGTH、窗口函数及数组聚合。CTE 内的 `来源.*` 会在执行阶段失败，逐列声明可执行。官方 [ARRAY_AGG 文档](https://doris.apache.org/docs/3.x/sql-manual/sql-functions/aggregate-functions/array-agg/)也明确数组元素顺序不保证，因此恢复顺序依赖全局位置，不依赖聚合返回顺序。

部分数组返回值并非合法 JSON，内部业务引号未转义。协议使用带 NULL 标记的 UTF-8 字节长度前缀，精确恢复字段和行边界，不按逗号或引号猜分割，不修改业务字符串。十进制按文本传输，避免打包时额外损失精度。分组缺失、重复业务键、错位、总量变化、字段缺失或截断均拒绝；上限 100000 行。仍通过原有 Consumer、Session、字段权限和分页校验，不另建跨身份缓存。

## 保留的限制

- 工作台仍有多次完整订单/准交查询，单次网关读取可达约 5～9 秒，本轮未取得数据库执行计划或服务端分段耗时，不能将整个网关耗时归为数据库执行时间。
- 当前 Hive 货龄查询返回 `RESOURCE_NOT_IN_DATASET`；负责人查询返回 `DATABASE_QUERY_REJECTED`。基线中这些命名调用也未返回行；本轮记录具体失败码，并将最终阶段区分为 `partial`，保留缺失原因，不补零、不代授权限。这些服务端问题尚未解决。
- 性能脚本拦截工作台自动报告保存，未对后台报告做写入；保存不属于本轮验收。
- 相邻 Manage 的 Windows 相同摘要快照 rename 竞争仍在；本地生成快照后重启独立 Host 才开始计时，未将准备失败计入页面结果，也未声称冷安装问题已修复。
