# 订单满足率根因分析与报告

从未满足的订单商品数量出发，定位重点对象，追溯供需约束及业务事件，输出有证据的结论或清晰的数据停止点。

## 按任务选择深度

- 口径问答、局部排查或页面修改，只处理相关内容；不强制执行完整诊断或生成报告。
- 完整根因分析包含口径审计、缺口定位、业务取证和报告交付。可按已有证据调整顺序、合并查询或跳过无关分支，不必遍历所有原因。
- 优先沿用用户给定范围和本轮已核验信息。仅在歧义会实质改变结果且无法查证时追问。

## 按需读取资料

- 取数、公式、维度映射、销售提报准确率：[指标与数据契约](references/metric-and-data-contract.md)。
- 库存、生产、物料、外协、调拨、仓配下钻：[诊断路径](references/diagnosis-paths.md)。仅选择相关分支。
- 证据评级、分析输出与核查闭环：[证据与输出契约](references/evidence-and-output-contract.md)。
- 生成或修改报告时，读取[交互分析契约](references/interactive-analysis-contract.md)及[报告数据契约](references/report-contract.md)。第四模块的结论生成规则也由报告数据契约维护。
- 首次接入、数据适配或环境排障时读取[输入准备](references/input-preparation.md)，复用适配与检测工具，不从零重建整套脚本。
- 需要提出业务假设时可参考[历史场景](references/historical-business-patterns.md)，不可将历史场景当作当前证据。

## 指标与取数原则

1. **指标定义由飞书指标清单及其关联 Cube 维护。** 核对指标编码、版本、公式、单位、统计范围和维度支持；本包中的字段与公式是核验线索，不覆盖现行发布口径。记录本次采用的口径快照；定义与实现冲突时暂停受影响结论，其他独立分析可继续。
2. 使用运行时实际登记的工具。通常由 `gea_kb` 查口径及业务背景，`cube_new` 查模型和数值；知识库回答不能代替业务取数。本轮已核验的模型可复用，范围或版本变化时重新检查。未知成员先查元数据，不靠猜字段形成正式结果；重试和批量大小遵循工具实际限制。
3. 订单满足率衡量已开订单商品的数量满足情况，不等同准交率。比例按正式聚合规则计算，不平均行级百分比；特别核对超发、零发货、重复、日期归属和源记录覆盖。汇总表不能代替底层非线性计算，不能用汇总后过滤修复汇总前的超发抵消。
4. 核心业务数量统一为**件**。源单位冲突时核验换算，未核验前不混算；原辅料可保留原单位作为证据。单位一致仍需匹配对象、订单池、期间、版本及供给关系。
5. 全国卡片、选中对象卡片和下级明细使用一致的指标定义，并按当前范围取数。初始与纠偏提报独立绑定；基地和品类是不同视角，不相加。模型新增基地等维度时刷新元数据及绑定，不沿用历史“不支持”结论。按完整分页和已核验映射聚合，不复制全国值、不按比例分摊填空。销售准确率使用正式双版本规则，不由提报总量或净差猜算。
6. 真实零值保留 0；缺失保留 `null`，显示“—”并说明原因。不以另一版本、示例值或其他指标补位；不擅自丢弃空值记录。全量汇总不能用 TopN 或首屏数据替代。
7. 记录查询来源、参数摘要、期间、筛选、粒度、版本、完整性与证据引用；仅成功返回的数据写入查询结果。已有可靠快照可用于用户允许的历史分析，但说明查询时间，不称为实时数据。

## 分析与证据边界

- 先判断异常是否来自口径或覆盖，再按缺货数量及贡献定位对象。两类缺货优先读取同一已开订单缺货数据集的正式度量；需要复核时遵循指标契约，不能用生产差额代替订单分类量。
- 从重点订单商品关联库存、生产、采购或调拨供给，核对需要时间、承诺时间、实际可用时间和数量。交叉指标用于选取核查方向，不直接证明因果；基地总量达标不能排除某一 SKU 或需要时点缺货。
- 生产 `deviation_reason` 保留原文并按 A–K 字典归组，规则见 `scripts/production-reason-dictionary.js`。仅展示有理由依据的分类；多标签不重复计量。生产分组正差、月度净差与订单缺货影响量分别表达，不相互替代。
- 有生产记录时可继续解释欠产机制，不因缺订单关联停在标签汇总；缺少日、产线等维度只限制相应判断。字典不替代理由原文，也不固定分析顺序。
- 区分有来源的事实 `verified_fact`、已验证根因 `verified_cause`、有支持待验证 `supported_unverified`、假设 `hypothesis`、缺数 `data_missing` 和口径冲突 `definition_conflict`。已验证根因需要对象关联、时间关系、作用机制与影响量依据，不能仅凭备注或相关性认定。
- 数据不足时说明已证明什么、还不能证明什么及如何补证，只停止受影响分支。数据质量问题放在审计与分析边界中，不制造业务原因或“尚未归类”指标块。
- 已验证原因给改善建议，未验证线索给核查建议；关联对象、责任角色与验收依据。未经授权不修改计划、写回系统或派发任务。

## 报告交付

完整分析默认在本 Skill 内交付 HTML、全量 Markdown 和数据文件；简短问答按用户需要输出即可。

1. 按报告数据契约整理 `report-data.json`，保留全量分析结果、来源与证据状态。第四模块围绕本期重要问题组织需求与供给结论，按证据选择对象、路径和深度，不固定对象、原因或段落数量；有条件时合并分析，不为凑框架强行归因。
2. 使用本包 `assets/订单满足率分析模板.html` 和生成器，保留既定布局、组件及交互，仅绑定真实数据。详细组件位置、原因联动、下钻和性能要求由交互契约维护，不自行另造简化页面。
3. 在 Skill 目录运行：

   ```text
   node scripts/report-environment.cjs
   node scripts/audit-report-data.cjs <report-data.json绝对路径> <审计输出.json绝对路径>
   node scripts/generate-report.cjs <report-data.json绝对路径> <输出目录绝对路径>
   node scripts/test-report.cjs <生成HTML绝对路径>
   ```

   DOM依赖优先用宿主已有模块，以 `DOM_TEST_MODULE` 绝对路径或工作目录配置复用；不可用时明确未执行，不循环安装。开发回归与业务验收分别记录。生成器附带源码指纹和数据审计；不能为通过测试改回旧口径。
4. 核对本期合计、分页完整性、对象切换、上下级绑定和空值/零值；全量结论不受页面筛选或 TopN 限制。响应式修改覆盖四个模块的指标卡、图表、宽表及展开下钻，按交互契约管理局部滚动。涉及视觉或交互的变更需浏览器验收，未完成则明确说明，不能以源码或 DOM 检查替代。
5. 交付文件与实际校验结果，明确剩余数据缺口，不把线索升级为根因。
