# DSH HTML 插件开发完整流程与注意事项

适用项目：`dsh-agent-workbench`、`dsh-agent-manage`、`dsh-gea-plugin`。依据当前仓库实现整理，核对日期：2026-10-16。

本文面向业务 HTML 插件开发，包括库存、产销协同等数据工作台。页面可以使用 React/TypeScript 开发，构建后由宿主加载 HTML；“HTML 插件”不等于只写一个 HTML 文件。完整交付包含页面、数据合同、资源声明、权限执行、构建产物和验收证据。

## 一、先明确归属和开发边界

| 所属 | 负责内容 | 不应放入的内容 |
| --- | --- | --- |
| Workbench | HTML/Native 页面、布局、筛选分页、页面动作、页面与 Session 关联、各 Agent SQL 配置 | 数据库密码、独立登录状态、第二套会话持久化 |
| Manage | Agent、Prompt、Skill、MCP 等资源及库存/APS 纯计算 | 页面布局、网络请求、权限授予 |
| GEA Host | 身份、凭据、Consumer、业务授权、受控查询及执行生命周期 | 页面私自决定的用户/租户身份 |
| DSH Core | 真实 Session、草稿、历史、预设及持久生命周期 | 业务页面自行复制的会话状态 |

业务页签可见、插件已安装、用户已登录、Consumer 获准、字段允许返回，是不同条件，必须分别检查。

当前这批库存插件的约定：

- 修改新版仓库；旧版 DSH 用作布局与业务含义参考。
- 布局以旧版为主，数据以新库可核实事实为主。
- 每个 Agent 的 SQL 集中在自己的配置文件中。
- 来源列表默认每页 10 行，翻页重新查询。
- 数据缺失显示 `-`，不能填零或编造值。
- 页面不出现“已覆盖”字样，使用统计日、有效记录数、来源范围等具体说明。
- 本轮数据适配只检查 `agents` 开头且名称不含 `wide` 的表。这是当前任务范围，不是所有项目的通用数据库规范。
- 不修改底层表结构；索引等数据库变更需要单独明确范围。

| 5 | 注册插件与资源声明 | plugin/page/capability 及 Manage 资源 |

### 1. 明确需求，不从表名反推业务

先列出旧版每个页签、卡片、明细列、筛选项、下钻和操作。对每个指标写明：

- 业务含义：库存、在途、销量、发货量、计划量分别是什么。
- 事实粒度：例如客户＋SKU＋统计日，或基地＋SKU＋计划月。
- 时间口径：统计日、上传日、生产日、加载时间、业务月份。
- 单位：箱、件、吨、元、万元、天，以及换算依据。
- 计算规则：公式、有效范围、分子分母、零分母、缺失处理。
- 数据权限与动作影响：只查看、修改视图、保存草稿或业务提交。

不能把“补全空白”理解为找任意相似字段填进去。页面保持原样，也可能需要重写取数和计算。

### 2. 确认开发目录、依赖和原始改动

先读取各仓 `AGENTS.md` 与现行开发文档，核对实际 checkout、分支、提交和未提交改动。不要因为目录同名就认定是本次开发目标。

从各仓 `package.json`、锁文件、支持的 Core 清单确认工具链。三仓固定输入、SDK 相对位置及公开导出必须兼容。不要用历史全局安装或其他工作树的可写输出顶替。

保留用户已有改动，不为了通过“干净候选”检查而清空工作区。日常修改可以在有在途改动的工作区验证；正式候选冻结与发行另按规则处理。

### 3. 先读表结构，再核实际数据

按用户允许的数据库和表范围执行只读检查，先收集：表注释、字段注释、类型、可空性、分区/键定义、行数、日期分布。

然后核对实际内容：

1. 关键业务键是否为空；是否真正唯一。
2. 字段非空数量、零值、负数、异常枚举及日期范围。
3. 表是当前快照、每日快照、流水还是月计划。
4. 关联前后行数和金额/数量是否放大。
5. 维度字段能否一对一关联；一对多时是否有合法选择规则。
6. 不同表的时间、单位、有效状态是否一致。
7. 新增表是否有数据；已有表是否新增列、删列或改变内容范围。

给每个结论标注核对日期。昨天为空的表今天可能有数据；结构相同也不代表数据口径未变。

不能只抽样看十行就断言字段完整。先对指定日期/范围做聚合核对，再抽查代表记录，避免无条件下载整表。

### 4. 建立字段映射和缺口清单

建议维护下表，一行一个业务字段：

| 页面字段 | 源表/源列 | 唯一键与日期 | 单位/公式 | 可用范围 | 缺失处理 |
| --- | --- | --- | --- | --- | --- |
| 在仓库存 | 经销商日表 `stock_qty` | 统计日＋客户＋SKU | 箱 | 同统计日有效记录 | 空值为 `-`；异常按明确规则处理 |
| 库存金额 | 经销商日表 `stock_amt` | 同上 | 元，已确认 | 源金额有值记录 | 不用猜测单价补算 |
| 支撑天数 | 在仓、在途、近30日动销 | 同一批记录 | 库存÷日均动销 | 三项均有效 | 缺依赖或零需求为 `-` |

缺口至少区分：物理缺列、表为空、列值为空、键无法关联、粒度不一致、单位未确认、权限拒绝、接口未接、请求失败。它们不能统一显示成“没有数据”。

优先寻找其他表中同粒度、同日期、同单位的事实。找不到就保留缺口，不按 SKU 把多个基地的值分给客户，也不把基地数据当分仓或经销商库存。

## 三、插件目录、声明与页面注册

当前库存插件的典型结构：

```text
dsh-agent-workbench/
  business/inventory-<agent>/
    plugin.json              # 页面包身份、入口、声明和配置路径
    page.json                # 页面标识、surface、协议、Consumer
    sql.config.json          # 本 Agent SQL 与字段/视图合同
    source/...               # 页面作者源；不同 Agent 内部路径不同
  business/shared/            # 查询客户端、字段格式化、分页等公共能力
  scripts/                   # 页面构建与验证入口
  lib/business/inventory-<agent>/
    index.html               # 构建输出
    plugin.json
    page.json
    sql.config.json
    capability.json          # 从 Manage 的所属资源装配
    prompt.json
    mcp.json
    skills/...

dsh-agent-manage/
  business-resources/inventory-<agent>/
    capability.json
    prompt.json
    mcp.json
    skills/...
```

路径以所选 Agent 的实际实现为准，产销协同不必强行改成其他插件的内部结构。

### 声明检查

- `plugin.json`：核对唯一 ID、名称、版本、HTML 入口、`sqlConfig`、声明路径和资源提供者。
- `page.json`：核对 `pageIds`、`surface`、`protocol`、`consumerCode`、可见性与允许影响级别。
- `capability.json`：由所属资源声明数据 tables/rules、启用状态与能力范围；不要靠扫描 HTML 或 SQL 猜能力。
- `prompt.json`、Skill、MCP：由 Manage 维护；页面不再建一份相同资源目录。
- 路径必须位于安装目录内；缺文件、ID 冲突、协议或 Consumer 不一致应明确拒绝。

当前 `gea-html-v2` 接收只读模块，不能通过改声明升级为业务保存、提交或审批。确有写业务需求，应走适用的受控能力协议并独立验收。

Workbench Host 的 `htmlRoots` 登记包内 HTML 来源，选页时读取正文。新增目录并不自动代表完成注册；显式配置了根目录时，还要检查目标根是否在登记范围内。

## 四、SQL 集中配置与数据执行

### 配置维护原则

每个 Agent 只维护自己的 `business/inventory-<agent>/sql.config.json`。页面引用查询 ID 和参数；不要在组件、点击事件或多个模块里散落同义 SQL。

现有主要字段：

| 配置项 | 用途 |
| --- | --- |
| `queries` | 新库命名查询、参数合同、返回列及分页配对 |
| `templates` | 旧链路兼容 SQL 模板；不作为新查询失败后的自动回退 |
| `sourceViews` | 来源页签、列、筛选和查询映射 |
| `sourceGaps` / `fieldGaps` | 当前数据或接入缺口 |
| `workspaceBindings` / `resultAliases` | 适用页面的新查询与原字段映射 |
| `overviewViewIds` | 适用页面的总览读取范围 |

具体结构使用同仓已验证配置，不凭空增加一个页面和执行器都不认识的字段。

构建把作者配置复制到 `lib`。Host 打开页面时读取包旁配置、校验身份和路径并注入，页面再消费。改作者配置后需要构建；不能只改源文件就认定安装目录已更新。正式发行包的配置变更也属于包内容变更，应重新定版发布。

### GEA SQL 硬性规范

任何 SQL、生成模板或 SQL 生成模型提示词修改前，都必须阅读 `gea-governed-sql/SKILL.md`；完整规则读同目录 `reference.md`，并做生成前自检。

- 只允许一条只读 `SELECT` 或非递归 `WITH ... SELECT`。
- 正式 GEA 查询只使用调用端提供的已发布资源和字段；物理库有表不等于已发布。
- 显式列、稳定且唯一的输出别名，禁止 `SELECT *` 与 `alias.*`，允许 `COUNT(*)`。
- 业务值使用命名参数 `:gea_pN`，不拼接用户输入；动态排序字段也不能由任意输入直接生成。
- JOIN 使用允许类型和显式 `ON`；禁止 `USING`、`NATURAL`、`RIGHT`、`FULL`、`LATERAL`。
- 禁止窗口函数 `OVER`、`DISTINCT ON`、递归/关联子查询及未批准函数。
- 类型转换使用 `CAST`，不使用 `::`。
- 取每组最新记录使用受控视图或 CTE＋最大日期回连；仍需处理同时间多条记录。
- 集合参数仅用于 `IN`；JSON 参数按规范传字符串；参数名不能使用保留前缀。
- 模型不得生成身份、租户、凭据、服务端权限表达式。

SQL 生成模型的输出协议与插件配置文件不同：模型输出遵循技能规定的 `sql / parameters / includeTotal`，配置文件则还包含页面与参数合同，不能混用两种结构。

### 明细、计数、汇总、快照分开

一个来源列表通常需要：明细查询、同口径 count、全筛选范围 summary，以及适用时的快照日期查询。

- 列表默认 `LIMIT 10`，下一页在服务端重新执行；稳定排序最后用唯一键兜底。
- 筛选和排序先在数据库作用于全集，再分页。筛选变化回第一页。
- 卡片汇总使用全部匹配记录，不能对当前十行求和。
- 所选日期之前取最近快照，不能偷用未来快照；是否跨月取旧快照取决于业务定义。
- 明细、count、summary 必须使用一致参数、快照和配置版本。
- 不重复叠加两层分页。新集中查询与旧 GEA 适配器不能各自再截一遍。
- 原业务需要完整事实计算时，不能先截十条再算。应在服务端计算后分页，或完整读取必要事实后计算并明确上限；未读全时不能宣称结果完整。

### 本地直连与正式 GEA 接线

本地直连仅作已授权的数据和页面核对。连接文件放忽略目录 `.runtime`，限制文件权限；凭据不进入 SQL 配置、HTML、前端变量、日志、截图或安装包。服务仅监听本机，页面提交查询 ID＋业务参数，不提供任意 SQL 执行接口。

当前这批集中查询的正式 GEA 执行器尚未接入；旧 GEA 页面仍沿既有链路。后续迁移步骤为：

1. 确认新资源和字段已发布，Consumer、数据源及返回权限可用。
2. 在 Host 侧解析可信安装配置，通过现有执行接口绑定真实身份与 Consumer。
3. 传递命名参数，保留 `returnedColumns`、`rejectedColumns` 和结构化失败。
4. 核对新库与正式资源字段、方言、日期、分页、额度和返回规模差异。
5. 验证部分字段拒绝、全部拒绝、取消、切用户及超时。
6. 使用真实宿主、真实已发布资源和真实授权链重放，再切换正式入口。

GEA 拒绝后不能静默退回数据库直连，也不能通过另一张未发布表补取受限字段。

## 五、计算正确性和显示规则

### 最容易取错的地方

| 问题 | 正确做法 |
| --- | --- |
| 计划月、统计日、上传日混用 | 分开保存和显示，写清每个筛选实际作用在哪个日期 |
| 交货量当客户动销 | 保留各自事实含义；没有等价证据不能替换 |
| 正常库存当目标库存 | 正常库存只展示源值，目标依赖明确业务阈值 |
| 上传日期当生产日期 | 上传日只表示提报时间，不能算货龄 |
| 多对多关联重复金额 | 先验证唯一关系或按事实键聚合，关联后再次对账 |
| 聚合后跨范围相加 | 统一记录范围后计算；不同小计分开说明 |
| 缺值转零 | `null`/空值保留未知；真实零仍显示零 |
| 负数一律删除或转零 | 查清冲销/退货等语义；保留明细，按明确规则汇总 |
| 比例平均、重复乘100 | 按业务分子分母计算，明确小数或百分数格式 |
| 每组任意取 MAX 去重 | 先确认重复原因；冲突记录不能任取一条冒充正确 |

本次经销商有效小计排除负数，是明确标示范围的核对口径，不是所有业务负数都应排除的通用规则。

### 经销商支撑天数实例

用户已确认日库存和动销为箱，库存金额为元。支撑天数采用同一批在仓、在途和30日动销均有效的记录：

```text
支撑天数 = SUM(在仓库存 + 在途库存) × 30 / SUM(近30日动销)
```

分母为零时保持未知。不能用甲批记录的库存除以乙批记录的销量，也不能把这个结果称作所有客户周转天数的算术平均。

### 缺口显示

卡片只显示必要的范围和日期，详细来源、有效行数、异常数量和公式放展开说明。大量解释文字会把卡片撑高，破坏旧版布局。

接口失败要有可操作错误提示；没有查到数据显示空态；权限拒绝显示权限原因；缺字段标明依赖。数字缺失显示单独的 `-`，不附单位。

## 六、页面、桥接和生命周期

沿现有入口等待桥就绪后读取数据，复用查询客户端、表格、格式化及上下文模块。纯计算放 Manage 的公开计算模块；页面负责选择条件和展示结果。

重点处理：

- 每次筛选、刷新、切客户都对应新的请求归属；旧结果不能覆盖新条件。
- 离页、切 Session、切用户或环境时取消/撤销旧读取并清理缓存。
- 取消前端请求不等于数据库执行已终止；不能虚报数据库已取消。
- 缓存至少考虑身份、数据范围、参数和配置版本；身份变更不能复用旧用户业务数据。
- 请求失败、超时、返回被裁剪或结果不完整，不转换成空数组后报成功。
- 同一请求的迟到结果只能归原请求；旧请求完成不能清掉新请求的加载状态。
- 清理事件监听器、页面动作、端口和引用，避免反复开页重复注册。

页面分析提供给 Agent 的上下文应包含查询条件、统计日、单位、有效范围和缺口。当前十行仅能描述为当前页，不能让模型当作全量事实；失败结果不能更新成“完整分析上下文”。

页面选取、插入草稿、发送模型请求、应用视图动作是不同能力。沿公开桥和 Core 草稿接口，不模拟宿主 DOM、不私建 Session、不擅自覆盖用户草稿。页面动作要声明实际影响范围，并保留取消和回执语义。

## 七、样式与旧版一致性

先对照旧版截图记录布局，再逐块替换数据。复用原组件、共享 CSS 和主题变量，避免为了接新表重做一套页面。

当前共享视觉规范的主要值：

| 项目 | 约定 |
| --- | --- |
| 字体 | Microsoft YaHei UI / PingFang SC / Noto Sans CJK SC / Arial |
| 页面底色 / 卡片 | `#f7f8fa` / 白色 |
| 主色 | `#df1732` |
| 卡片主数字 | 23px、700，数字与单位间距3px |
| 卡片圆角 / 间距 | 10px / 常用12px |
| Tab 选中 | 品牌色文字＋2px底线 |
| 表头 / 数据行高度 | 38px / 43–44px |
| 表格分页 | 参照计划管理：总数靠左，页数选择和翻页靠右；控件统一 36px，菜单不得被表格裁切。完整状态与窄屏规则见 `workbench-ui-style/references/style-spec.md` 的 Table pagination 节。 |
| 宽表 | 横向滚动，不能隐藏必要字段或压扁文本 |

风险、预警和成功色保留语义，不被普通 Hover 覆盖。按钮、Tab、输入框和可点击卡片必须有键盘焦点样式。

至少检查1280宽度及较窄窗口，观察长客户名、长金额、单位换行、卡片高度、弹窗、筛选栏和表格横向滚动。若本次约定以旧版布局为主，不能借“统一规范”擅自改导航和业务信息层级。

## 八、加载速度优化顺序

先记录实际耗时，区分页面构建/资源加载、快照查询、数据库扫描、网络传输和渲染。不要只看 SQL 返回十行就认定查询很轻。

1. 默认只加载当前页签需要的数据；其他页签和弹窗打开时再读。
2. 大表先限制客户、统计日、计划月等有效条件，不默认扫全客户明细。
3. 服务端筛选、排序、分页；只取页面需要的列。
4. 能用源日期字段过滤时，避免在过滤列上做无必要的转换，保留分区裁剪机会。
5. 多表先限定范围并处理粒度，再关联；避免重复扫描和重复聚合。
6. 独立读取可有界并发，依赖快照日期的查询等日期确定后再执行。
7. 元数据可短时缓存；业务结果缓存必须有身份隔离、失效策略和时效说明。
8. 检查执行计划、实际行数、耗时和资源使用，再判断索引是否有收益。

使用 MySQL 协议连接不代表底层就是 MySQL。这次后端是 Doris，索引、分区和执行计划按实际引擎判断，不能照搬 MySQL 的索引语句。索引也属于 DDL，不能经受控 SQL 网关执行。本轮不改底层结构，应先完成查询和加载策略优化，必要时另交数据库变更建议。

保存一次首屏、连续翻页、切客户、切日期和大范围查询的实际耗时，写清环境和样本。单次0.9秒只能说明该次测试，不代表生产环境性能承诺。

## 九、分层验证和构建

### 数据验证

- 用独立源表聚合核对数量、金额、客户数、SKU数及有效行数。
- 核对同一客户/日期的列表、汇总和详情是否一致。
- 验证零、空、负数、重复键、旧快照、无快照及零需求。
- 第1/2页默认各10行，在同一稳定数据集内不重不漏；筛选后count同步变化。
- SQL可执行只是第一步，还要核对业务含义与用户看到的范围。

### 行为和权限验证

选择与改动相关的现有测试，重点验证取消、迟到结果、配置版本变化、缺返回字段、部分失败和授权失败。不要为了增加测试数量编写只复述实现的测试。

正式 GEA 必须验证部分字段拒绝时的展示、全部拒绝时的失败，以及权限错误不重试、不回退、不绕过。读取结构化 `stage / reasonCode / statementPath / suggestedAction`，据原因修正。

### 页面验证

实际打开构建后的页面：检查总览、页签、筛选、翻页、弹窗、刷新、错误与空态。查看控制台和请求情况，并与旧版截图比较。源码检查或构建成功不能替代浏览器验证。

### 当前页面构建入口

下面命令在 Workbench 仓运行，依赖和同组 Manage 资源先按本地开发文档准备。同一工作树的 `lib` 写入串行执行。

```sh
node scripts/build-inventory-dealer.mjs
node scripts/build-inventory-fc.mjs
node scripts/build-inventory-qll.mjs
node scripts/build-inventory-aqkc.mjs

```

这些是页面级构建。完整插件构建、官方SDK类型检查及质量门禁按仓库开发文档和任务输入执行，不用页面构建替代。

构建后检查 HTML、声明、SQL 配置、Manage 资源是否齐全；源配置与产物配置是否一致；构建来源与摘要是否匹配。只改作者源，生成的 `lib` 和打包文件由构建产生，不手工修编译后的大 HTML。

本地服务若无热更新，构建后重新加载页面；截图应来自最终产物，不能拿旧截图证明新版本。

## 十、打包、安装和发布

以下是开发交付流程说明，不表示当前任务已经授权发布。当前隔离仓库的远端和正式运行目录边界仍按各仓 AGENTS 与实际任务范围执行。

1. 固定源码、版本、依赖锁和支持的 Core/三仓组合，完成所需构建与检查。
2. 按现有打包入口生成普通插件包、清单、SHA-256和安装说明；核对包内公共入口、声明、HTML及SQL配置。
3. 包中不能有数据库连接、Token、`.runtime`、个人路径、开发链接或另一套宿主SDK。
4. 在独立测试环境通过普通插件安装链验收实际 Loader、Host与资源接收。
5. 再核 Native/HTML 页面、真实登录、业务查询、字段权限及受影响的生命周期。
6. 获得对应发布范围后，按公司发行路线固定包、更新目标频道并读回验证；不自动沿用历史GitHub/npm发行流程。
7. 正式版从合并后的主分支固定源码构建；同版本必须对应固定字节，内容改变就用新版本。
8. 检查远端并发变化，保留其他插件的频道修改；不覆盖旧包或移动旧标签。
9. 完成发布后记录包、频道、源码和本地同步状态；更新器/入口/依赖变化按影响范围补做真实安装、重启与数据保留验证。

必须区分这些结论：页面构建成功、包已生成、安装与Host接收通过、浏览器/Native运行通过、真实业务权限通过、正式频道已发布。每一步只陈述实际证据。
